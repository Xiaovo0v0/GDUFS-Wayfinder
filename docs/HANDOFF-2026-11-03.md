## 三、用户看到的是「没反应」，而不是「服务挂了」

改前的 `navigator-ui.js`：

- `parseBlock()` 只处理 `message` / `agent_message` 的 `d.answer`、`message_end`、`error` 三种事件；
- 失败时 Dify **不发 `error` 事件**，只发 `workflow_finished(status=failed)`；
- 于是 `acc` 恒为 `""`，`.then()` 里 `parseJson("")` → `null` → `finish({answer:""})`；
- 结果：**渲染一个空气泡**，徽章仍显示「在线 · Dify」。

这就是「问了没反应」的全部机制。模型侧挂掉是外因，**前端把外因吞掉**才是这个 bug 的真正可修部分。

## 四、这次改了什么（`gdufs-3d/navigator-ui.js`，`node --check` 通过）

1. 新增 `shortErr(e)`：把几百字的 PluginInvokeError 压成一句人话——`Connection refused` → 「模型服务连不上（Connection refused）」，超时 → 「模型服务超时」，5xx → 「模型服务返回 5xx」，其余截 80 字。
2. `parseBlock()` 里，`var d = ev.data || ev;` 之后新增：

   ```js
   if (ev.event === "workflow_finished" && (d.status === "failed" || ev.status === "failed")) {
     if (!acc.trim()) throw new Error("Dify 工作流失败：" + shortErr(d.error || ev.error));
   }
   ```

   （注意：必须放在 `var d` 之后，否则 `var` 提升让你读到 `undefined.status`，直接 TypeError。）
3. 调用侧 `.then(function (raw) { … })` 开头加空内容兜底：`if (!String(raw || "").trim()) throw new Error("Dify 返回空内容（模型服务未响应）");` —— 走 `.catch()`，落到本地规则。
4. `window.__uiBuild` 由 `"stream-3"` 改为 **`"stream-4"`**（页面里搜这个词就知道跑的是不是新包）。

改后失败路径的最终文案：「…（Dify 未响应：Dify 工作流失败：模型服务连不上（Connection refused），已切换到本地规则）」，徽章 `离线 · 本地规则`。

**单文件版已重打**：`node tools/build_single_file.mjs` → `gdufs-3d/dist/index.html` 与 `gdufs-3d/dist/广外校园向导.html` 各 **2797950 B**（22:27），已含本次补丁，且内联了 `ai-config.local.js` 的 app key（1 处）。两个文件 UTF-8 无 U+FFFD。

## 九、追加：路口斑马线（`renderCrosswalks`）

> 用户 m00611 手绘了一张十字路口：**每条进口一条斑马线**，要求照这个做。
> 先在 Blender 里出了理想十字与真实路口的对比图（`artifacts/blender/junction_crosswalk_preview.png`、
> `junction_real_preview.png`），用户 m00699 选定范围：**只做 4 臂、正交 ±20°、单幅（臂宽 ≤ 13 m）**。

**第二轮（用户 m01505 打回重做）**：页面截图上「双幅路交叉」的黄实线直接从路口中间穿过去，
白虚线又在斑马线条与条之间的缝里露出来。根因两条：

1. 一个物理路口在数据里被拆成 2~4 个小盘（中环东路 × 广外东路拆成 4 个，相隔 7~17 m），
   盘与盘之间露着车行道 ribbon，而标线是**烘在 ribbon 贴图里**的，所以黄线穿过路口；
2. 白条之间是 1 m 缝，缝里露出的是同一条 ribbon 的虚线。

**改法**（`gdufs-3d/app.js`，整段替换 `renderCrosswalks`）：

- **分组**：只取 `arms.length === 4 && rings.length` 的盘，按中心距 < `GROUP_R = 16` 用并查集合并
  （南校 74 个 → 55 组，最大 4 个一组，不会连成长链）。组内统一决策，避免各画各的。
- **走廊盖面**（`junctionCover`）：同组两块盘沿同一条路相邻（夹角与某条臂差 < 20°、距离 3~25 m），
  就在两盘之间铺一条宽度 = 两盘臂宽较小值的沥青带，y=0.6045、`polygonOffset -18/-36`、同一张
  `asphaltTex`。**没有用凸包**：凸包会把四条腿之间的草地尖角一起盖成沥青（试过，草楔子明显被吃掉）。
  中心线穿过路口的那一段正好被这条带压住。
- **中央补块**：四条走廊围出来的中间那块是分隔带，留草地会像「路中间长草」。用组内各盘中心点
  围出的多边形按 1.35 倍外扩补上（不会碰到四条腿外头的草地楔子）。
- **同一材质**：盖面直接用路口补面的 `juncMat` 实例（同一张 `asphaltTex`、同一套 uv/12 标定），
  不新建材质——否则盖面和补面之间会看出一条色差接缝（用户 m01685 说的「中间那块颜色不一样」）。
- **横道垫层**（`crosswalkBase`）：每条腿在 y=0.6055 铺一块矩形，从本盘边界一直铺到横道外沿，
  缝里不再露虚线；黄线停在斑马线跟前。
- **位置**：`tEdge` 只从**本盘**边界量（不再用整组凸包，否则横道会被推到盘与盘之间的空当里）；
  内腿判定改成「`tEdge + 1 m` 的点落在整组凸包里」→ 这条腿指向组内另一个盘，跳过。
- 闸门沿用：4 臂、正交 ±20°、单幅（臂宽 ≤ 13 m）、`arm.open`、`onOtherRoad()` 命中沥青、
  带宽按脚下 ribbon 实际半宽收；横道本身 y=0.607、`polygonOffset -24/-48`。

**实测数据**：南校 **75 条横道 / 287 根白条 / 574 三角面**，走廊盖面 24 面、垫层 150 面；
北校 26 条 / 289 根 / 578 面（北校没有需要合并的多盘组，盖面 0 面、垫层 52 面）。三个 mesh，每校区仍是 1 个 draw call 一组；
`roadGroup.userData.crosswalks` = 横道条数（不再是 0）。

### 1. 登录入口不是 172.17.1.46

`http://172.17.1.46/signin` 的页面是能打开的，但它内部的 API base 是 **`https://dify.gdufs.edu.cn`**（登录页会去打 `dify.gdufs.edu.cn/console/api/refresh-token`）。在 `172.17.1.46` 上提交表单会跳到 `/auth/refresh` 再弹回登录页，**永远登不上**。正确入口：**`https://dify.gdufs.edu.cn/signin`**（解析到 202.116.196.186，和 172.17.1.46 是同一套后端；同一个 app key 打 `/v1/parameters` 两边都 200）。

登录后的 CSRF：cookie 名是 **`__Host-csrf_token`**（JWT 串），不是 `csrf_token`；请求头带 `x-csrf-token: <该值>`，否则控制台 API 一律 `401 CSRF token is missing or invalid`。（`GET /console/api/apps/<id>/workflows/draft` 例外，不需要 CSRF。）

## 十、路口斑马线：黑色盖面的根因与重做（2026-11-05）

用户 m01685 要求「中间重叠部分和正常道路同色」，m01743 追问「路口为什么变成黑乎乎的一坨」。

**根因不是贴图，是三角形绕序反了。** `renderCrosswalks` 里 `rect()` / `rect2()` 输出的三角形是顺时针（CW），而 WebGL 正面是逆时针（CCW）；材质又是 `DoubleSide`，背面三角形的法线被翻成 -Y，只剩环境光 → 整块 `(8,12,12)`。白色横道条因为颜色接近纯白、环境光下还看得见，所以一直没被发现。判断方法：把盖面材质临时改成 `side: THREE.FrontSide`，整块消失就说明是绕序问题。**贴图、法线、阴影、polygonOffset 都不是原因**（都逐一证伪过）。

修法：

- `rect()` 的三角索引改成 `[0,2,1, 0,3,2]`，`rect2()` 改成 `a,c,b`，统一 CCW；
- 盖面改回 `juncMat`（`asphaltTex` 那张 128² 无标线沥青图），和路口补面同材质、同 uv 标定（1 贴图 = 12 m）、同 polygonOffset（-16/-32），颜色就和正常路面一致；
- 盖面形状：整组所有盘 `rings` 的凸包，向质心收 0.6 m 后扇形三角化。**不要用「盘对盘连线铺矩形」**——双幅路斜对的两块盘会连出一条 45° 的宽带，横着切过路口（踩过）；
- 横道仍是每腿一条：`tEdge` 从本盘边界量起，`mid = tEdge + 1.0 + 3.4/2`，条 0.45 m、间距 1.0 m，垫层从 `tEdge` 铺到横道外沿，黄线正好停在跟前；
- 闸门保留：4 臂、正交 ±20°、臂宽 ≤13 m、`open`、`onOtherRoad` 命中；`onAsphalt()` 额外接受「落在本组任一 ring 内」（盘里不是 roadIndex 的地盘）。

**当前计数**（`tmp/cwtest.mjs`，南/北）：横道 75 / 26 条，白条 287 / 289 根，574 / 578 面；盖面 165 / 60 面，垫层 150 / 52 面。单文件包已重打（`gdufs-3d/dist/*.html` 各 2,808,572 B）。

截图（真机，`node tools/shot.mjs --compose --nohud`）：`artifacts/review/junction_fixed_close7.png`（中环东路 × 广外东路 26 m 机位）、`junction_area_mid.png`（全景）。

**本会话截图环境的坑（下次直接用）**：沙箱拦 Chromium 的 mojo 命名管道，`node tools/shot.mjs` 起不来浏览器。两条路：① 用 `Start-Process` 在沙箱外起 `msedge --headless=new --remote-debugging-port=9333 --no-sandbox --disable-gpu`，再跑 `shot.mjs`（它会自动 attach）；② 若 Edge 只监听 `[::1]:9333`，用 `tmp/v4proxy.mjs`（TCP 127.0.0.1:9333 → [::1]:9333）做后台 job 常驻。注意 `shot.mjs` 结束会 `b.close()` 关掉浏览器，每次截图都要重新起。

## 十一、双幅路口：一条跨全宽的横道 + 不再铺成一整块广场（2026-11-05 夜）

用户 m02052 发来一张真实十字路口航拍照（「获取公开地图的数据，可以参照这个十字路口画」），
m02103「继续执行」。照片里三条特征：路口是一整块沥青、四个角是圆弧路缘、斑马线一条横跨整条路
（含中央分隔带）。这一轮先解决第二条和「整块沥青」的形状问题。

### 改法（都在 `renderCrosswalks` 里）

1. **按盘盖面，不用整组凸包**。双幅×双幅的路口在数据里是 4 个盘，整组凸包是一个约 25 m 见方
   的大广场，四角的沥青会压到人行道上。改成每个盘各自 `convexHull(rings)` 向内收 0.6 m 再铺。
2. **中心补一块**：盘与盘之间那几米空地是中央分隔带断口，取「各盘中心点围成的凸包」向外放
   5.5 m 铺上，四角草地不碰。
3. **按进近方向聚类，合并双幅**：腿先收集成 `legs[]`（每条腿记 `{盘心, ux/uz, t0, w, a}`），
   再按方位角 12° 聚类。同一进口的两幅车道平行、并排，落进同一簇 → 一条横道跨全宽，
   条数按 `span` 算。横道位置取「各盘沿该方向能走多远的最大值 + GAP + DEPTH/2」，
   即整组路口的最外缘；每个盘各退一截的话，横道会跑到路口中间（踩过，见 `_j7.png`）。
4. **端点回缩**：进口道在路口附近会变宽变窄，`hi/lo` 按盘宽算出来的跨度经常多出半米，
   落在人行道上。从外侧每 0.5 m 往里收，直到 `onOtherRoad(...,0.45)` 成立；收完还不足
   2.5 m 就整条丢掉。

### 计数

`node tmp/cwtest.mjs`（南校）：`bands 66 / verts 2100 / tris 700 / coverTris 190 / baseTris 132`。
（原来 75 条腿 → 合并后 66 条横道；南校 4 臂正交单幅路口的双幅进口被并到了 9 处。）

### 截图（真机，非预览）

- `artifacts/review/_j9.png`：中环东路 × 广外东路（-180,-422），四个进口各一条跨全宽横道，
