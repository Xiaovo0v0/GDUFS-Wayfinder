## 二、语料是怎么来的

```
data/service_guide/service_items_lite.json  ──┐
data/official/buildings_teaching.json       ──┼─ tools/make_dify_corpus.mjs ─→ data/dify/service_guide_qa.md (12.6 KB)
data/official/life_area.json                ──┘                              data/dify/campus_wiki_qa.md   (17.0 KB)
```

- 每条语料是一个 `Q: ... \nA: ...` 块，块与块之间空行分隔。
- 入库时用 **自定义分段**：分隔符 `\n\n`，`remove_extra_spaces` 关、`remove_urls_emails` 关——保证一个 Q&A 对正好是一块。

### 踩过的坑：Q&A 分段会卡住

一开始用 `doc_form: qa_model`（Q&A 分段模式），文档索引状态一直卡在 `splitting`，5 分钟不动；同样的文件用 `text_model` 10 秒就完成。**结论：这台服务器上不要用 Q&A 分段，用「通用 + 自定义分隔符 `\n\n`」代替**，检索效果一样（每块仍是一个完整问答对）。

## 三、应用结构（6 个节点）

```
开始 → 意图识别(LLM) ─┬─→ 检索办事指南(知识检索) ─┐
                      └─→ 检索校园百科(知识检索) ─┴→ 生成回答(LLM) → 直接回复
```

| 节点 | 作用 | 关键配置 |
|---|---|---|
| 开始 | 接收 `sys.query` | 无变量 |
| 意图识别 | 输出 JSON：`{intent, from, to, place}`，intent ∈ navigate/service/wiki/chat | temperature 0.2，要求"只输出 JSON" |
| 检索办事指南 | 查 40 条办事事项 | TopK 4 + rerank |
| 检索校园百科 | 查 61 条建筑档案 | TopK 4 + rerank |
| 生成回答 | 汇总两路检索 + 意图，输出最终 JSON | 提示词里约束"不要编造房间号/电话" |
| 直接回复 | `{{#llm_answer.text#}}` | — |

**为什么两个检索都跑**：不分支、结构最简单、失败面最小；靠提示词里的"只用相关资料"兜住噪声。40+61 条语料的检索成本可以忽略。

### 提示词加固（踩坑记录）

第一版提示词太松，出现了一次明显的编造：问"图书馆几层？"，模型答"共 5 层，1-4 层阅览区，5 层办公区"，还给了"周一至周日 8:00-22:30"这种知识库里没有的时间。

加固做法：

1. 在提示词里把两段检索结果显式标注为【检索结果·办事指南】/【检索结果·校园百科】，并写死"**只允许使用检索结果里出现的事实**"；
2. 点明高风险字段："层数、房间号、电话、时间、金额，检索结果里没有就写官网未公布，**绝对不要凭印象补**"；
3. 检索结果为空时的固定兜底话术；
4. `temperature` 0.2 → 0.1，TopK 4 → 6。

加固后同一组问题全部答对（图书馆 6 层、文采园三餐时段、成绩单办理地点与电话），不再出现编造。

### 提示词要点

- 意图识别里**内置了 48 个规范地点名**（正门、图书馆、教学楼A栋…），要求 from/to 必须用这些名字——这样前端才能直接匹配到 3D 场景里的对象。
- 生成回答要求输出固定 JSON 契约，并明确"官网未公布的信息就说没公布，不要编房间号和电话"。

## 四、前后端契约

前端 `gdufs-3d/navigator-ui.js` 调用 `POST /v1/chat-messages`（`response_mode: blocking`），
从 `answer` 字段取出下面这个 JSON：

```json
{
  "intent": "navigate|service|wiki|chat",
  "from": "文采园（第一饭堂）",
  "to": "图书馆",
  "answer": "从文采园出发……约 820 米，步行 10-12 分钟。",
  "card": { "title": "文采园→图书馆", "desc": "经地下隧道，约 820 米", "url": "" }
}
```

前端拿到后：

| intent | 前端动作 |
|---|---|
| navigate | 用 `from` / `to` 匹配场景地点 → 画路线 → 相机飞到路线中点 |
| service / wiki | 在对话里渲染回答 + 卡片（卡片带「查看官方页面 ↗」） |
| chat | 只渲染文字 |

> 兼容性：模型偶尔会把 JSON 包在 ```` ```json ```` 里，前端 `parseJson()` 会先剥代码块再解析。

## 五、离线兜底

Dify 在内网，评委的网络环境不一定能连上，所以前端做了双通道：

| 通道 | 触发条件 | 能力 |
|---|---|---|
| 在线 | `/v1/chat-messages` 200 | 意图识别 + 两库检索 + 生成 |
| 离线 | 请求失败 / 超时 / 无密钥 | 地名匹配（导航）+ 40 条 FAQ 关键词检索（办事），数据在 `gdufs-3d/faq-data.js` |

界面上右上角的徽章会显示当前通道（**在线 · Dify** / **离线 · 本地规则**），失败时回答末尾也会注明原因。

实测：把密钥改坏后，问"文采园到图书馆怎么走"仍能正确画出 820 米路线；问"校园卡丢了怎么办"能返回校园卡管理办公室的地点、材料、流程和电话。

## 七、已知限制与下一步

1. **跨域/混合内容**：页面若是 `https://` 部署，浏览器会拦截 `http://172.17.1.46` 的请求（混合内容）。当前验证环境是 `http://127.0.0.1:8765`，正常。公网演示要么用 http 站点，要么给 Dify 配 https/反代。
2. **密钥暴露**：`ai-config.js` 里是 WebApp 级密钥，只能调这一个应用；公开仓库前建议换成环境注入或临时密钥。
3. **路线由前端算**：Dify 只给 from/to，实际路网计算在浏览器里（220 节点 Dijkstra）。好处是断网也能用；后续可以把算路做成「工作流工具」，让 Dify 直接返回 polyline。
4. **多轮上下文：已开启**。两个 LLM 节点的记忆窗口都打开了（size 10），前端会带上 `conversation_id`。
   实测：「从文采园怎么去图书馆？」→「那从图书馆再去二饭呢？」能正确解析为 图书馆 → 博雅园（第二饭堂），约 800 米。
5. **MCP 未启用**：应用已支持，但需要在集成里装 `MCP server` 扩展才能对外暴露。
