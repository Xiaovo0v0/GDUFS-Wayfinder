# 定位「我的位置」：方案、实现与 Dify 边界

> 状态：已实现并通过验收（`tools/check_locate.mjs` 17/17、`tools/smoke.mjs` 10/10）
> 涉及文件：`gdufs-3d/geo.js`（新增）、`gdufs-3d/app.js`、`gdufs-3d/index.html`、`gdufs-3d/i18n.js`、`gdufs-3d/navigator-ui.js`、`tools/check_locate.mjs`（新增）

---

## 一、先说结论

1. **定位本身用不上 Dify，也不该用。** 定位是浏览器权限 + 每秒变化的前端状态：`navigator.geolocation` 拿 GPS，投影到本地坐标系、贴路网、画标记、算路都必须在前端完成。绕一趟大模型只会更慢（实测 Dify 分支 4–5 秒）、更不准（模型算坐标必错），而且断网就废——这跟作品「双通道降级、断网可用」的设计直接冲突。
2. **Dify 该用在「定位之后的语言层」**：听懂“我这里怎么去图书馆”，把模糊说法归一成标准地名，解释“你附近有什么”。这部分已经用**不改 Dify 的方式**接上了（见第五节方案 A）。
3. 想再拿“多 Skill 集成”的分，可以加第 5 个技能 `nearby-poi`（输入一个地点或经纬度，返回附近设施排序）——这是 Dify 真正擅长的形态，见方案 B。

## 二、功能拆成四件事

| # | 用户看到的行为 | 技术实现 | 归属 |
|---|---|---|---|
| 1 | 点「📍 我的位置」，地图飞到我所在的地方 | `navigator.geolocation.watchPosition` → WGS84 → 校园本地坐标 | 前端 `geo.js` |
| 2 | 地上出现蓝点 + 精度圈 +「我的位置」标签 | Three.js 圆面/圆环 + Canvas Sprite | 前端 `app.js` |
| 3 | 起点自动变成「我的位置」，选终点就能算路 | 把定位点贴到最近路网节点，作为一个临时 `place` 参与 Dijkstra | 前端 `app.js` |
| 4 | 问「我这里怎么去图书馆 / 我附近有什么」 | 本地规则秒回；在线时把“我这里”归一成“我现在在图书馆附近”再问 Dify | 前端 `navigator-ui.js`（Dify 零改动） |

## 三、坐标系：这是整个功能的命门

`gdufs-data.js` 的 `meta` 里已经有两校区的本地坐标系定义，南校区还有一套 WGS84 原点：

```js
origin_wgs84: { lon: 113.39215489681557, lat: 23.066554348076398 }
crs_local: "x=镜像后横向(m，西为正), z=北向(m), y=高度(m)"
```

投影（`geo.js` 的 `project()`，与 `tools/add_water_lines.mjs` 用的是同一套）：

```js
KX = 111320 * cos(lat0)      // 广州约 102.4 km/度经度
KZ = 110540                  // 约 110.5 km/度纬度
x  = -(lon - lon0) * KX      // 注意负号：模型是镜像的，西为正
z  =  (lat - lat0) * KZ
```

| 项 | 数值 | 说明 |
|---|---|---|
| 投影误差 | < 2 m / 全校区 | 等距圆柱近似，在 1.6 km 范围内足够 |
| 手机 GPS 精度 | 5–30 m（室外） | 状态栏直接显示 `accuracy` |
| 精度圈半径 | = `accuracy`（米） | 不是装饰，是 GPS 自己报的 68% 置信半径 |
| 贴路网偏差 | 实测 8.8 m | 用最近路网节点当起点，偏差画成接驳段 |

**为什么必须处理 GCJ-02**：规范上 `navigator.geolocation` 返回 WGS84，Chrome/Edge/Safari 也是；但部分国产浏览器/WebView 直接返回高德坐标，在广州会偏 **400–500 m**——足以把“图书馆门口”定位到校外。`geo.js` 内置了 `wgs2gcj / gcj2wgs`，用 `?geo=gcj` 打开反算；定位点落在校界外 80 m 以上时，状态栏会主动提示。

## 四、代码怎么接的

```
index.html  ── <button id="btnLocate"> ── <script src="geo.js">（在 app.js 之后）
                                        │
geo.js  ── project(lat,lon) ────────────┤
        ── __navDebug.setMyPosition(x,z,{accuracy}) ──┐
                                                      │
app.js  ── setMyPosition()  ── nearestNode(x,z)        │  贴路网
                            ── drawMyMarker()          │  精度圈 + 点 + 标签
                            ── startPlace = myPlace    │  当起点
                            ── route()                 │  复用现有 Dijkstra / 画线 / 漫游
                            ── flyTo(x,z,...)          │  镜头推过去
```

对外只加了一个入口，其余全是复用：

```js
window.__navDebug.setMyPosition(x, z, { accuracy, lat, lon })  // → {x,z,node,snap,routed}
window.__navDebug.getMyPosition()                              // → {x,z,accuracy,snap,nearest}
window.__navDebug.clearMyPosition()
window.__navDebug.nearestPlace() / .nearbyPlaces(k)            // 给对话层用
```

`findPlace('我的位置')` 也认这个临时点，所以 AI 动作契约里的 `from` 可以直接写「我的位置」，`walk.js` 的第一人称漫游同样能从这里出发。

**没有改的东西**：路线算法、动作契约、Dify 的任何节点、单文件打包逻辑（`build_single_file.mjs` 按 `index.html` 里的 `<script src>` 自动内联，新文件不用登记）。

## 五、Dify 到底能不能用上

| 方案 | 做法 | 改动量 | 值不值得 |
|---|---|---|---|
| **A. 前端归一（已实现）** | 问句里有“我这里/我的位置”时，给 Dify 补一句「我现在在<最近地标>附近。」；拿回 `navigate` 动作后，前端用**真实定位点**重算路线 | Dify 零改动 | ✅ 推荐：稳、快、断网也能用 |
| B. 新增 `nearby-poi` 技能 | Workflow：输入 `place` + `k`，Python 代码节点算最近设施，输出 `[{name, dist, bearing}]`；主应用加“附近有什么”分支 | 1 个 DSL + 1 条分支 | 想做“多 Skill 组合”加分时值得 |
| C. 经纬度塞进 Dify `inputs` | 主应用 start 节点加 `loc_lat / loc_lng`，提示词里让模型描述位置 | 改 DSL → 重新导入 → 换模型要同步 | ❌ 不推荐：模型算不准坐标，还多一跳延迟 |

方案 A 的细节（`navigator-ui.js` 的 `withMyLocation()` / `applyAction()`）：

- 为什么要**前置**一句而不是替换原句：主应用算路代码节点是按**地名出现顺序**取前两个地名（`cands.sort()` 后取 `names[0]`、`names[1]`）。前置“我现在在图书馆附近。”正好让 `from=图书馆`、`to=用户说的目的地`，Dify 12 个节点一个都不用动。
- 为什么拿回动作后要**重算**：Dify 给的距离是“从最近地标”算的，地图上必须从“我”这里画。前端 `route()` 会用真实起点重算，状态栏的数字才是权威。
- 最近地标会**排除问句里已经出现的地点**，避免出现“图书馆附近 → 图书馆”。

如果要做方案 B，`nearby-poi` 的输入输出建议：

```yaml
# 输入
place: 图书馆        # 或 lat/lng 二选一
k: 5
# 输出
{"ok": true, "from": "图书馆",
 "items": [{"name":"文采园（第一饭堂）","dist":312,"bearing":"南"},
           {"name":"教学楼B栋","dist":188,"bearing":"东南"}]}
```

把 POI 表（61 条百科 + 50 个地点 + 经纬度）用 `tools/` 里的小脚本从 `gdufs-data.js` 生成 Python 字面量塞进代码节点，不要手写——手写必然和地图漂移。

## 六、坑与边界（答辩会被问到）

| 现象 | 原因 | 处理 |
|---|---|---|
| 手机用 `http://192.168.x.x` 打开，点定位没反应 | 定位 API 只在**安全上下文**可用：HTTPS / localhost / `file://` | 局域网演示换 HTTPS 或内网穿透；本地双击 HTML 是 `file://`，可用（已实测） |
| 双击本地 HTML 能不能定位 | Chrome 把 `file://` 视为安全上下文 | ✅ 已实测：授权后正常出点、能算路 |
| 北校区点按钮提示不支持 | 北校数据是官方平面图矢量化（0.4178 m/px），`meta.origin_wgs84` 为 `null` | 需要 2 个控制点做仿射配准才能上定位，属下一步 |
| 室内/地下车库一直“正在定位” | 没有 GPS 信号，只能等网络定位 | 15 秒后状态栏提示“到窗边/室外” |
| 点落在楼里，路线从“楼外”开始 | 贴的是最近**路网节点**，不是建筑出入口 | 校门已有 `access_dist`；下一步可对所有建筑出入口做接入点 |
| 手机返回高德坐标，点偏 400 m | GCJ-02 偏移 | `?geo=gcj` 反算；校界外 >80 m 自动提示 |
| iOS 要求用户手势才能弹权限 | 浏览器策略 | 按钮点击本身就是手势，没问题 |

## 七、验收

```bash
# 起服务
py -3 -m http.server 8080 --directory gdufs-3d

# 定位专项（CDP 伪 GPS，不需要真手机）
node tools/check_locate.mjs            # http://127.0.0.1:8080
node tools/check_locate.mjs --file     # 额外验一遍双击本地 HTML

# 原有回归
node tools/smoke.mjs                   # 10/10
```

`check_locate.mjs` 用 `Browser.grantPermissions` + `Emulation.setGeolocationOverride` 模拟“用户允许定位 + 手机在正门”，断言：

- WGS84 → 场景坐标偏差 < 1 m（实测 0.00 m）
- 精度取用 GPS 上报值、贴路网距离 < 60 m
- 起点自动切到「我的位置」、状态栏给出最近地标
- 能从「我的位置」算出路线（正门 → 图书馆 452 m / 16 个路点）
- 再点一次能取消定位
- 全程零未捕获异常

在线链路（Dify 在校内网，本机连不上）用「打桩 fetch」验过一遍：问「我这里怎么去图书馆」，实际发给 Dify 的 query 是
`我现在在正门附近。我这里怎么去图书馆？`，拿回 `{"intent":"navigate","to":"图书馆"}` 后前端把起点换成真实定位点，
状态栏显示 `我的位置 → 图书馆 452 米`。也就是说 Dify 的 12 个节点不用改。

没有 GPS 的笔记本演示/截图：

```
http://127.0.0.1:8080/?ll=23.06829,113.3946,15      # 正门，精度 ±15 m
```

## 八、下一步（按性价比）

1. **北校区配准**：在官方平面图上取 2 个已知经纬度的控制点（如正门、体育馆），算旋转+平移+缩放，填进 `north-data.js` 的 `meta.origin_wgs84` + 一个角度参数。有了它，北校定位立刻可用。
2. **贴边而不是贴点**：现在是最近节点，改成投影到最近**边**并插一个临时节点，能把 8.8 m 的接入误差降到 1–2 m。
3. **朝向**：`coords.heading` 在移动中才有值，可加一个指向箭头；静止时用 `deviceorientation` 补。
4. **室内**：真要进楼，只能上蓝牙信标/UWB 或扫码定位，和 GPS 是两条线，不建议在初赛阶段碰。
