## 六、评委可能追问的 8 个问题（提前准备）

**Q1：你的算路为什么要在前端和 Dify 各写一份？**
A：前端那份保证断网可用（评委可能遇到内网抖动）；Dify 那份让智能体能独立发布为工具、被别的应用复用。两份共用同一份路网数据（220 节点 / 239 边），由脚本从同一源生成，不会漂移。这是"降级"而非"重复"。

**Q2：多智能体是"真"多智能体吗？**
A：诚实说，是**路由 + 专家分支**的工程实现：一个分类器把问题分给四个专家节点，每个专家有独立的系统提示词、独立的检索上下文、独立的工具。它具备多智能体的核心特征（分工、隔离上下文、各自调工具），但不是多个独立进程互相通信。如果要求严格的多 Agent 对话协议，我们现在没有做。

**Q3：知识库的召回效果怎么证明？**
A：抽样验证了 12 条常见问题，TopK=6 + 重排后答案要点命中 11 条。**没有做系统化的召回率评测**，这是我们的短板，如果有时间会补一个 40 题的评测集。

**Q4：数据从哪来？会不会过时？**
A：11 个院部官网的一手页面 + 广州市规划验收合格证（层数/面积）+ 学校官方平面图（北校轮廓）+ OSM/Overture（南校轮廓与路网）。每条办事数据记录了 `src` 与 `confidence`，官网未公布的明确写"官网未公布"而不编造。更新方式是重跑 `tools/make_service_data.py`。

**Q5：如果办公室搬了怎么办？**
A：`place_map.json` 里地点是按事项独立存的，改一行就能更新，不用动提示词。这是我们把"数据"和"逻辑"分开的结果。

**Q6：为什么用 Dify 不用 Coze/扣子？**
A：① 作品是"自定义 3D 前端 + 智能体"，需要 Service API 让前端驱动渲染；② 多智能体、多 Skill、RAG 三项能在同一个应用里组合；③ 学校自部署，发布即生效，不受第三方审核周期影响。

**Q7：单文件 HTML 1.7 MB，加载会不会慢？**
A：本地双击打开约 1 秒；走 HTTP 首屏 1.2 秒（实测）。GLB 用 LOD2、树用 InstancedMesh、贴图程序化生成，所以体积压得住。

**Q8：三个人月做了这些，如果多给一个月做什么？**
A：按优先级：① 补知识库召回评测集；② 北校也做 GLB（现在只有南校有）；③ 接入校历，让"营业状态"能识别寒暑假与节假日调休。
